# EZ ERP architecture

## Stack

| Concern | Choice | Why |
| --- | --- | --- |
| UI | Flutter (Android, iOS, Web) | One codebase, as required |
| State | Riverpod 2 (no code generation) | Simple providers, easy testing |
| Routing | go_router with a shell route | Deep links on web, redirect guards |
| Backend | Supabase: Postgres, Auth, Storage, Realtime | Row level security fits multi-tenant ERP |
| Fonts | Manrope (headings, figures), Inter (text) via google_fonts | Legible tabular figures |
| Charts | fl_chart (added with dashboards data) | Mature and fast |

SEO is not a concern, so the web build is a plain Flutter app (CanvasKit renderer).

## Folder layout

```
lib/
  core/        config, theme tokens, router, session state, permissions, utilities
  shared/      reusable widgets and the CRUD engine
  shell/       sidebar, top bar, global search, responsive frame
  features/    one folder per product area (auth, dashboard, settings, ...)
supabase/migrations/   numbered SQL files, applied in order
docs/
```

## Multi-tenancy and access control

- Every business table carries `org_id`. A user can belong to several organizations (companies); the active one is
  stored locally and switched from the top bar. This is the foundation for Phase 3 multi-company.
- Authorization is enforced in the database. Policies call `has_permission(org, module, action)`, which resolves
  the caller's role. The Flutter UI mirrors the same permissions only to hide what a user cannot use.
- Roles and permissions are data: `roles` and `role_permissions` (view, create, edit, delete, approve, export per
  module). The Owner role bypasses checks. Owners cannot be removed or demoted by non-owners, and the last active
  owner cannot be removed.
- Branch scope is stored on the membership (`branch_ids`, empty means all). It is applied to branch pickers now and
  to branch-aware tables as they arrive.
- New tables get standard policies with one call: `select public.apply_org_rls('public.table', 'module')`.
- Every important table gets an audit trigger with `select public.enable_audit('public.table')`.

## Router registry

`core/router/nav.dart` lists every screen in the product plan. `core/router/feature_routes.dart` lists the screens
that exist. Any navigation entry without a registered screen opens a roadmap page, so shipping a module is one line:
register its route. The sidebar, phone Modules page and global search all read from the same map and hide entries the
user's role cannot view.

## CRUD engine

`shared/crud` renders a complete master-data screen from a `CrudConfig`: searchable list (table on wide screens,
cards on phones), create and edit form (dialog or bottom sheet), archive instead of delete, permission checks and
friendly error messages. Customers, suppliers, products, warehouses, units, categories and accounts reuse it.
Screens that need nested lines (invoices, purchase orders, vouchers) get purpose-built forms.

| 0007_reports | SQL views and functions for dashboards and reports |

Design rules:

- Financial records are never deleted. Mistakes are fixed by reversal or adjustment vouchers.
- Posting (documents to ledger and stock) happens inside Postgres functions so it is atomic.
- Receivables and payables are derived from invoices, bills and payment allocations, not stored twice.
- Money uses `numeric(18,2)`; quantities use `numeric(18,3)`.

## Master data notes

- Customers and suppliers share one `parties` table. A party can be both. Customer screens are governed by the sales
  permission, supplier screens by purchase; row level security checks the flags.
- Codes (CUS-00001, SUP-00001, ITM-00001) are generated by database triggers from the numbering rules, so they stay
  unique under concurrent use. Rules are editable in Business settings; the next number can only move forward.
- Products are readable by anyone who sells, buys, requests or stocks items, and writable by inventory roles.
- Financial figures (purchase price, standard cost, opening balances) are hidden in the app from roles without the
  financial figures permission. This is a screen-level control for now. Hiding them at the database level needs
  column privileges or a separate view and is scheduled with the reports step.
- The CRUD engine loads lists in pages of 1000 and filters on the device. Very large catalogues move to server-side
  search in step 1D when stock quantities join the list.

## Finance engine

- Double entry: every posting is a voucher with lines that must balance (debits equal credits, amount above zero,
  every line on an active non-group account). The check runs in the database, not only in the app.
- Vouchers move draft, pending, approved, posted (or rejected, back to draft). Posted vouchers are immutable: triggers
  block updates and deletes even for administrators. A mistake is fixed by a reversal, which posts an equal and
  opposite voucher and flags the original. Reversals cannot be reversed again.
- Vouchers, lines, cash and bank accounts and expense entries have no direct write policies. They change only through
  SECURITY DEFINER functions that check permissions explicitly (save_voucher, submit_voucher, approve_voucher,
  post_voucher, reverse_voucher, save_expense, pay_expense, record_income and others).
- Cash and bank accounts each wrap one ledger account under 1110, 1120 or 1130. An opening balance posts a journal
  against Opening balance equity.
- Expenses follow request, approval, payment. Payment creates and posts the payment voucher. Income is recorded and
  posted in one step. Cancelling a paid or received entry reverses its voucher.
- Ledgers and balances are computed from posted lines by account_ledger and account_balances, so they can never
  disagree with the books. Employees can see accounts (to pick an expense head) but not vouchers or balances.
- Attachments follow the permission of the record they belong to. A new record gets its id on the device first, so a
  bill can be attached before the first save. Photos can be taken on phones.
- Seeded chart of accounts is a neutral starting point. System accounts (receivable, payable, inventory, sales, cost
  of goods, tax accounts, opening balance equity) have keys that later steps post to.

## Offline behavior

Phase 2 adds a local draft queue on mobile: unfinished forms are stored safely and synced when the network returns,
with visible state. Phase 1 screens fail with a clear message and a retry action.

## Conventions

- All UI text is English, in sentence case. No emojis anywhere.
- Buttons say what they do ("Save changes", "Send invitation"). Errors say what happened and what to do.
- Delete is replaced by archive, cancel or reverse wherever history matters.
- Currency shows with lakh and crore grouping when the company currency is BDT.
- Tax, VAT and e-invoice rules stay configurable. The software never claims legal compliance.
- AI outputs, when they arrive in Phase 4, are advisory and never change financial records without confirmation.
